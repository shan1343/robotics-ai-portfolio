# Learning, second brain and cross-surface continuity
Use the existing provider objects; this is not a new memory database. CURRENT.md remains authority.

## REOPEN
For whole-lecture or cross-surface continuation, apply [source coverage](source-coverage.md): recover the full current unit from exact pointers, carry unread/deferred units forward, and distinguish verified links from inspected content and actual learning. The receiving surface's access remains untested until observed.
For “continue” or a new review session, treat the existing Notion course page as the source index rather than assuming the Project already contains every source. For a narrow supplied question, skip unrelated retrieval.
1. Fresh-read the course page's Learning Profile, last checkpoint, Sources & Identity and exact source/result pointer.
2. Fetch the exact Drive object from that pointer. Reuse a verified matching LM Export; do not regenerate it merely because Work/NotebookLM is available.
3. Only if the pointer is missing/stale, run one bounded Drive search by course + date/week + material type and verify candidates from body SESSION_ID/source coverage/official source. Search failure is UNKNOWN, not absence.
4. Load only source material needed for the current study scope and at most 1–2 relevant Wiki articles.
A checkpoint contains only course/session identity, source/artifact pointer and coverage/version, actual last question/attempt outcome, unresolved point and next useful action. Keep it in the existing session/course section or Learning Profile, not a new handoff file. Same-Project context helps but is not automatically a verified checkpoint.
A receiver re-reads the provider object before continuing. If current tools cannot recover it, mark SOURCE PARTIAL/UNSAVED as applicable and continue within verified material; no invented mode switch, dispatch, result or “already synchronized”. No routine user copying of prompts, file IDs or Work results. One genuine course/session clarification is preferable to silently choosing the wrong class.

## WRITEBACK
At a material learning turn or natural stopping point, reflect observed evidence when current standing authorization and the connector allow it. **Ordinary Chat should perform this writeback directly when its Notion connector is callable; a Work commit is not mandatory.** Do not require “save” or “today is done” as magic words. Avoid per-token/per-question logs and duplicate summaries.
Record error type, source/problem location, observed attempt, correction, whether hinted or independent, unresolved next practice. Leave the user's grades and attendance unknown unless evidenced. Read back the exact changed section.
The next relevant session must actually use the saved lesson. A successful write is persistence proof, not proof of later learning improvement. No answer from the learner means no learning assessment.
If write access is absent, preserve the concise checkpoint in the current chat and disclose unsaved status; do not say it is durable or secretly switch stores. Use the existing Brain candidate path only within its permissions, not as another Task database.

## WIKI / second brain
The existing private personal-ai Wiki stores curated source-backed concepts, derivation/solving strategies, useful worked examples, relationships, important corrections and reusable procedures. Current tasks, deadlines and routine lecture transcripts stay in their providers. Update an existing related article instead of appending another summary. Preserve source links and distinguish outside synthesis from course facts.
Select the existing personal-ai Wiki explicitly when the current working project has an unrelated .wiki. On Galaxy Book, use the native llm-wiki hub registry/config to find that named existing wiki; do not create another corpus. At read time check the selected identity and minimal index. Query is read-only: no reindex or capture just to answer a question.
Ordinary Chat can read the same already-preserved Markdown through its GitHub connector in the existing private repository; it does not need to run the local Wiki plugin. Local-only edits are not automatically in GitHub. Reconcile approved changes through the existing repository; never promise instant cross-surface sync.
Use 1–2 relevant articles when they change the answer; do not load all memories every time. Existing Fourier trigger, for example, should change a relevant period/coefficient setup rather than merely be mentioned.
A reusable lesson may be captured as a noncanonical candidate under current approval. Canonical synthesis/promotion needs source verification in an active relevant/authorized maintenance session. Do not auto-promote every ordinary Chat turn or let a Codex session hook claim to observe ordinary Chat.

## PORTFOLIO
Meaningful academic engineering outputs, experiments, substantial project results or instructive failed/partial attempts can update the existing Portfolio & Attempts hub and related Case. Routine review/each wrong answer is not a portfolio entry.
Preserve user contribution, AI contribution, team contribution when applicable, source/artifact evidence, verified result, unverified claims, and the next changed decision. Do not inflate an AI-written solution into student competence or setup tests into academic improvement. Reuse the existing Case for the same trajectory, no duplicate Portfolio DB. Keep private course material private and final sharing separately approved.
