# Maintaining Academic Loop
This is a bounded procedure for the assistant, not extra work the student must operate.

## Interpret feedback
ONE_TIME: “오늘은 짧게”, “이번에는 문제 내지 마” changes this task only.
PERSISTENT: “앞으로 복습에서는 ...”, “다음에도 적용되게 고쳐” authorizes the bounded requested procedure update, subject to protected boundaries.
LEARNING_EVIDENCE: an observed mistake/independent success goes to the existing learning record, not an automatic code change.
Unclear frustration is evidence of a problem, not permission for silent global preference/security rewrites. Explain the exact intended persistent change briefly; ask only when material intent remains ambiguous.

## Edit source, verify installed behavior
Locate the actually loaded plugin and its author-owned source via current marketplace/runtime metadata. Never infer a marketplace root by concatenating a path to marketplace.json. Cache-only changes are not durable source updates.
Read the current relevant files and version; preserve concurrent changes; back up the source and install metadata. Use a small failing example or regression check before editing. Keep the same four entrypoints unless a new workflow is genuinely needed.
Edit only relevant source files/references, preserve approvals/source fidelity and private data boundaries, validate references/manifest and regression cases. Bump the source version. Use the host's supported existing local plugin install/update action; do not delete all plugins or change trust/auth settings.
Re-read the resulting installed version and compare source/installed content hashes. Start a fresh supported read-only session for a representative behavior check. Structural tests are not real GUI or learning acceptance. If a current session has stale instructions, use a new session; do not assert hot reload.
Report what changed for the student, actually loaded version/behavior, limits and rollback. On regression restore only this change from its backup via the supported installation path. No self-authorized merge, public publication, new subscription or permission expansion.

## Borrow before building
For a demonstrated recurring defect, prefer an existing native feature, current specialist tool, accepted template, or reviewed OSS procedure. Inspect license, runtime compatibility, permissions and costs before use. Keep origin/version when borrowing code. Do not install a whole overlapping harness to fix one task; compare on the same real outcome before making it default.
