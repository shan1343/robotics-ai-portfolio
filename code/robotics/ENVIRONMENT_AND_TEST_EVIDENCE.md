## A. Zone별 충돌 환경을 구성하는 코드

대회 환경을 시각적 장면으로만 표시하면 MoveIt 경로계획의 collision checking에는 반영되지 않을 수 있습니다. 보존된 `skill_primitives/environment.py`(2026-05-25 개발 snapshot)에는 **작업대·다리·부품 상자·트레이·혼재 객체를 collision object로 등록**하는 코드가 있습니다.

**당시 코드가 수행하려던 기능은 다음과 같습니다 (원본 팀 코드는 비공개 보존).**

~~~text
원본 코드 기능을 설명하는 절차: 환경 객체 등록/해제, TF 기준 변환.
실제 팀 Python 코드 전문은 공개하지 않습니다.
~~~

등록 대상은 `setup_zone_a/b/c/d`와 `remove_zone_a/b/c/d`로 분리했습니다. 작업 구역 전환 시 기존 객체를 정리하고 현재 구역의 장면을 설정하려는 목적입니다. 오른팔·왼팔 인터페이스에서 동일 전역 Planning Scene에 add/remove가 경쟁적으로 전달되는 문제를 당시 코드 주석에서 발견해 **단일 publisher로 등록 경로를 좁힌 수정본**이 보존돼 있습니다.

**주의:** 당시 코드에는 `client.moveit2_r`와 실제 `MoveItClient._moveit_r` 노출 방식의 버전 차이도 남아 있습니다. 인터페이스 정합성은 6/3 별도 개발일지에서 문제로 기록되었으며, 모든 변경본이 하나의 실행 상태에 동시에 반영됐다고 단정하지 않습니다.

## C. 좌표계: 움직이는 로봇과 고정된 책상

보존된 6월 25일 미커밋 mission 작업본에는 `FRAME_ID = "base_link"`에서 `FRAME_ID = "odom"`으로 바꾸고, `odom ← base_link` TF를 조회한 뒤 물체 좌표를 변환하는 패턴이 있습니다.

문제는 환경 객체가 `base_link`에만 고정되면 로봇 이동에 따라 책상과 장애물이 따라다니는 것처럼 표현될 수 있다는 점입니다. 개발 기록은 **작업 구역 진입 시 측정한 상대 좌표를 odom 고정 좌표로 옮기는 방법**을 제안합니다.

**보존된 작업본의 기능을 요약합니다 (원본 Python 미재배포).**

~~~text
원본 코드 기능을 설명하는 절차: 환경 객체 등록/해제, TF 기준 변환.
실제 팀 Python 코드 전문은 공개하지 않습니다.
~~~

위 코드는 *원본의 의도를 확인하기 위한 발췌*로, 그대로 실행 가능한 완성 함수가 아닙니다. 원본에는 TF 예외·timeout 처리 및 회전(quaternion)에 의한 좌표 변환도 있습니다. **미커밋 작업본이므로 팀 main 반영 여부와 실제 이동 후 테스트 성공은 확인되지 않았습니다.** TF 조회 실패 시 base 좌표를 그대로 쓰는 fallback은 안전한 `odom` 배치를 보장하지 않아 후속 검증 대상입니다.

## D. MoveIt IK·작업공간을 어떻게 검증했나

**2026-06-02 본인 개발일지 기준.** 실제 실물 파지·운반 시험의 성공률이 아닌 **mock hardware / 시뮬레이션 기반 계획 시험**입니다.

| 시험·문제 | 당시 기록 | 의미 |
|---|---:|---|
| `test_moveit_client` | 12/12 | 연결·FK·입력 검사 |
| `test_arm_motion` (플러그인 누락) | 0/47 | 로봇 자체 문제보다 IK 의존성 오류를 먼저 의심 |
| `test_arm_motion` (TRAC-IK 설치·T2 재시작 후) | 42/47 | 경로계획 결과 회복. 파지 성공률이 아님 |
| `test_workspace_d` 1차 | 35/53 | 경계 포즈 탐색 |
| `test_workspace_d` 확장 | 53/84 | x/y·pitch 조합을 확장해 제한 조건 확인 |

개발 기록에는 위치·pitch 결합 시 reachable 영역이 달라지고 `is_pose_safe()` 초안을 만들었다는 내용이 있습니다. 예를 들어 **x=0.150 m일 때 pitch ~20°**는 그 환경의 시험 기록이며 실제 로봇 동작 가능 영역 일반화는 금지합니다.

TRAC-IK는 `kinematics.yaml`에 설정됐지만 실제 컨테이너에 plugin이 없어 `failed to load`가 발생했고, 설치 뒤 결과가 바뀌었습니다. 따라서 이 사례의 핵심은 **실패를 로봇 하드웨어의 제약으로 바로 단정하지 않고, 계획 노드가 사용하는 의존성과 실행 순서를 확인한 과정**입니다.
