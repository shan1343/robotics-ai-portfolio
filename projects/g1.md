[첫 화면](../README.md) · [보존된 Flat 실행 설정](../evidence/g1/flat-settings.yaml)

**2026.03–현재 | 실물 조작 · Isaac Lab / RSL-RL 실습 · 보상 설정·재학습 시도 · 팀 실행·평가 준비**

3월에는 지지장치 환경의 G1을 직접 조작·실행하고 촬영했습니다. 이후 원격 GPU에서 Isaac Lab의 보행 학습을 실행하면서, 어떤 움직임에 보상을 주고 어떤 움직임을 억제할지 설정을 바꾸는 실습을 했습니다. 관심은 로봇이 움직이는 영상만 보는 것에서 **입력 관측, 출력 행동, 보상과 실행 환경의 관계를 이해하는 것**으로 넓어졌습니다.

## 실습 영상과 설정의 관계

실물 G1과 RL 영상의 원본은 교수·CTO 제한 Notion에 보존합니다. 영상 제작·재게시 권한과 개인 checkpoint와의 대응이 아직 확인되지 않아 공개 저장소에 복제하지 않았습니다. 아래는 실제 코드·설정과 실험 해석입니다.



교수·CTO용 Notion에는 2026.03.19 실물 조작 영상과 시뮬레이션 영상을 나란히 두고, 별도의 RL 낙상 후보도 보존했습니다. 실물 영상은 이 공개 후보 저장소에 포함하지 않습니다. 이 자료들은 각각 활동의 흔적이며 **같은 학습 정책의 시뮬레이션→실물 전이 결과나 개선 전후 쌍은 아닙니다.** 영상과 개인 checkpoint의 직접 대응은 아직 확인하지 못했습니다. 무접미사 영상의 지형 판독은 로컬·Drive의 서로 다른 동명 파일 기록이 있어 파일명만으로 확정하지 않습니다. RL (4)의 회수본은 과거 재생 검사에서 오류가 기록돼 대표 자료로 사용하지 않습니다.

## 무엇을 다뤘는가: 로봇·환경·정책·학습을 분리

| 요소 | 확인한 내용 | 아직 확인되지 않은 것 |
|---|---|---|
| 로봇 설정 | 보존된 기본 Rough 소스가 `G1_MINIMAL_CFG`를 사용 | 이 설정의 관절 수를 최신 팀 G1 29DoF와 동일하다고 가정하지 않음 |
| 학습 환경 | `G1RoughEnvCfg`는 `LocomotionVelocityRoughEnvCfg` 상속, Flat은 Rough를 상속해 평면으로 변경 | 상위 환경 전체와 해당 run의 최종 병합 config |
| 관측 | Flat 코드에서 `height_scanner`와 `observations.policy.height_scan`을 제거 | 이 파일만으로 전체 관측 벡터 차원·순서를 복원할 수 없음 |
| 행동 | 별도 보존 Flat 설정에 joint-position action scale 0.5 | 출력 차원·관절 순서와 checkpoint의 정확한 대응 |
| 학습 실행 | 개인 기록에 Isaac Lab의 RSL-RL train/play 실습과 재학습 시도 | run의 `agent.yaml`, actor/critic 폭, PPO 세부 계수 |
| 현재 팀 연구 | 속도 추종 보행과 달리 영상 기반 참조 모션 추종·실행·전환·평가를 조사 | 팀 정책을 개인이 처음부터 개발·실물 배포한 성과가 아님 |

현재 팀 문서의 actor/critic `[512, 256, 128]` 등을 과거 개인 학습 모델로 옮겨 적지 않았습니다. 정책이 모터 torque를 직접 출력한다고 설명하지도 않습니다. 확인한 Flat action 설정은 정책 출력을 기준 자세·배율과 함께 **관절 목표 위치**로 사용하는 형태입니다.

## Rough 보상: 발을 더 들게 하는 것과 움직임을 억제하는 것의 균형

원본 `rough_env_cfg.py`와 수정 후보들을 직접 비교했습니다. 기본 파일에는 선속도·회전속도 추종, 발 체공, 발 미끄러짐, 관절 한계와 기본 자세 이탈에 대한 항목이 있습니다. 수정 후보는 발 체공 보상을 높이고 토크·관절 가속도·action 변화·몸체 기울기의 페널티를 완화하는 방향입니다.

| 항목 | 기본 보존본 | 수정 후보 `(2)`에 적힌 값 | 설정을 바꾸려던 방향 |
|---|---:|---:|---|
| `feet_air_time` | 0.25 | 0.75 | 발을 들고 있는 행동의 보상 비중 증가 |
| `dof_torques_l2` | −1.5e−7 | −5.0e−8 | 토크 사용 페널티 완화 |
| `dof_acc_l2` | −1.25e−7 | −5.0e−8 | 관절 가속도 페널티 완화 |
| `action_rate_l2` | −0.005 | −0.001 | 연속 명령 변화에 대한 페널티 완화 |
| `flat_orientation_l2` | −1.0 | −0.5 | 몸체 기울기 페널티 완화 |
| `undesired_contacts` | `None` | weight −1.0, threshold 1.0, hip/knee 링크 지정 | 원치 않는 신체 접촉을 억제하려는 설정 |

이 표는 **보존된 파일 간 코드 비교**이지, 변경값 전부가 실제 학습에 적용됐다는 결과표가 아닙니다. 페널티를 줄이는 것은 actuator 출력 한계를 바꾸는 것과 다르며, 체공 보상을 늘린 비율이 보행 성공률의 개선 비율도 아닙니다.

### 검수에서 발견한 소스 결함

수정 후보 `rough_env_cfg (2).py`에서 `__post_init__`가 `G1RoughEnvCfg` 클래스 바깥, 모듈 수준으로 정의돼 있었습니다.

```python
# 발견한 구조를 축약한 설명. 실행용 설정 파일이 아님.
@configclass
class G1RoughEnvCfg(LocomotionVelocityRoughEnvCfg):
    rewards: G1Rewards = G1Rewards()

def __post_init__(self):  # 이 파일에서는 클래스 밖에 존재
    ...
```

따라서 해당 함수 안에 적힌 robot·event·reward·command 변경을 클래스 초기화에서 적용되는 설정이라고 읽으면 안 됩니다. `feet_air_time=0.75`처럼 별도 `G1Rewards` 클래스에 있는 값과 함수 안의 변경도 적용 경로가 다릅니다. 이번 편집에서는 원본을 몰래 고쳐 실행 성공으로 만들지 않고 **수정 시도와 실제 적용 증거를 분리**했습니다. 어느 파일이 실행 당시 import됐는지와 완성된 환경 config를 찾아야 적용 여부를 판단할 수 있습니다. 이 결함을 MuJoCo sim-to-sim 실패 원인으로 연결할 근거도 없습니다.

## Flat 보상: 과도하게 발을 드는 움직임을 줄이려던 수정

`flat_env_cfg.py`와 `flat_env_cfg (1).py`는 둘 다 terrain을 `plane`으로 바꾸고 terrain generator·height scan·terrain curriculum을 제거합니다. 후자의 주석에는 ‘2차 수정’이라는 설명과 함께 다음 변경이 남아 있습니다.

- `feet_air_time.weight`: **0.75 → 0.2**. 주석에 기록된 의도는 과도하게 발을 드는 ‘장난감 병정’ 같은 움직임을 줄이는 것입니다.
- `joint_deviation_hip.weight`, `joint_deviation_torso.weight`: 각각 **−0.5**로 지정해 기본 자세 이탈을 억제하려 했습니다.
- `base_height_l2`와 target height 0.75 제안은 **주석 처리**되어 있습니다. 적용된 보상 항목으로 집계하지 않았습니다.

```python
# flat_env_cfg (1).py의 실제 설정 발췌
self.rewards.feet_air_time.weight = 0.2
self.rewards.feet_air_time.params["threshold"] = 0.4
self.rewards.joint_deviation_hip.weight = -0.5
self.rewards.joint_deviation_torso.weight = -0.5
```

두 파일의 차이와 주석으로 수정 의도는 설명할 수 있지만, 어느 checkpoint가 이 버전으로 생성됐는지나 수정 뒤 동작이 좋아졌는지는 별도 실행 근거가 필요합니다. **Rough에서는 체공 보상을 높이고 Flat 수정본에서는 다시 낮춘 두 맥락**을 하나의 성능 향상 이야기로 합치지 않습니다.

## sim-to-sim 실패와 후속 과제

MuJoCo의 모델 로딩·실행 단계로 정책을 옮기려던 시도는 실패했습니다. 최초 오류 로그는 아직 확보하지 못했습니다. 관측 차원·관절 순서·기준 자세·quaternion·action scale·PD gain·제어 주기는 확인할 항목이지 확정된 원인이 아닙니다. 보존 화면 판독의 `--exp_name` 인자 오류나 다른 프로세스의 checkpoint 생성도 이 실패의 원인과 결과로 합치지 않습니다.

후속 검증에서는 실제 사용된 환경/agent config와 checkpoint를 묶고, 동일한 명령·초기조건에서 policy 재생을 비교해야 합니다. **이번 작업은 과거 자료 분석이며 새 학습·MuJoCo 실행·실물 로봇 시험을 수행한 것이 아닙니다.**
