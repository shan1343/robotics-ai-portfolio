# Personal AI — 만들면서 배운 검증과 중단의 기준

[포트폴리오 첫 화면](../README.md)

**기간: 2026년 9월 | 역할: 제품 요구·수용 기준 정의, AI 작업물 통합과 실제 사용 평가**

저는 아직 자율적으로 움직이는 개인 비서를 완성한 엔지니어가 아닙니다. 학업 일정과 개발 작업을 덜 놓치고 싶어서 Personal AI를 시작했고, AI 작업자들이 만든 기능을 실제 계정과 업무에서 시험하며 무엇을 믿을 수 있는지 배우는 중입니다. 코드를 많이 생성했다는 사실보다, 기존 데이터를 잘못 고치지 않았는지, 작업자의 PASS가 실제 결과와 같은지, 새 기술이 제 수고를 줄였는지를 기준으로 결정을 바꾼 기록이 이 프로젝트의 핵심입니다.

제가 맡은 일은 문제와 허용 범위를 정하고, 확인할 증거를 요구하며, 결과를 읽고 통합·중단을 결정하는 것이었습니다. 연동과 코드 구현, 테스트·리뷰의 상당 부분은 AI 작업자들이 수행했습니다. 아래의 [JavaScript 검증 모듈](../code/personal-ai/src/lived-canary-evidence.js)도 그 산출물로 소개합니다. 저장소의 코드량을 제가 손으로 작성한 양이나 독립적인 소프트웨어 구현 능력으로 환산하지 않습니다.

## 1. 공식 마감 변경: 이미 있는 과제의 다른 값을 지키기

**2026-09-17 학업 일정 시험.** 공식 안내에서 마감이 바뀌면 기존 Task를 찾아 그 마감만 갱신해야 했습니다. 제목만 보고 새 Task를 만들면 중복되고, 통째로 덮어쓰면 사용자가 적어 둔 실행 시각·우선순위·상태·완료 여부·메모가 사라질 수 있습니다. 관련 자료도 전체 Drive에서 막연히 검색하지 않고 해당 과목 범위에서 확인하도록 요구했습니다. 공식 발신자와 기존 과제의 대응 관계, 변경 허용 필드, 저장 후 다시 읽는 절차를 수용 기준으로 정했습니다.

개인 식별 정보를 뺀 **개념적 입출력**은 다음과 같습니다. 실제 Task 원문이나 계정 데이터를 복제한 예시는 아닙니다.

| 단계 | 확인할 상태 |
|---|---|
| 입력 | 공식 마감 안내 + 이미 존재하는 해당 과제 Task |
| 변경 | 동일 Task의 공식 마감 필드만 갱신 |
| 보존 | 실행 시각, 우선순위, 상태, 완료 여부, 메모 |
| 재조회 | 기존 Task의 갱신값과 보존 필드 비교, 새 Task 중복 여부 확인 |

당시 기록에는 기존 Task **UPDATE**, 다른 필드 보존, 중복 생성 **0건**, 명시적 과제 분류 AI 호출 **0회**, 관련 파일 발견과 잘못된 누락 경보 없음이 적혀 있습니다. 이는 **한 번의 범위가 정해진 시험**에 관한 결과입니다. 새 Task가 없는 경우의 CREATE 경로, 반복 운영의 누락률, 절약한 시간은 확인되지 않았습니다. 더구나 9월 19일 재감사는 이 수치의 근거가 작업자가 남긴 provider 관찰 기록이며 원 Make 실행과 Task 버전을 독립적으로 다시 열어 확인한 것은 아니라고 구분했습니다. 따라서 현재 운영 중인 자동화의 성능 수치로 제시하지 않습니다.

이후 넓은 쓰기 권한의 위험과 미완료 경로가 남아 있어 해당 Make 경로와 Task writer를 비활성화했습니다. 당시 설정 재조회 기록에는 감시 간격을 2시간에서 4시간으로, 학업 관련 기동을 하루 14회에서 8회로 줄인 것도 남아 있습니다. 한 번 잘 바뀐 Task가 자동 쓰기 전체를 승인하는 근거가 되지는 않았습니다. 다음 학습 과제는 같은 대응·보존 규칙으로 누락 Task의 생성 경로와 반복 실사용을 별도로 검증하는 것입니다.

**원본 근거:** 비공개 개인 저장소의 `development_evidence/archive_mining_20260919/04_PORTFOLIO_EVIDENCE_BANK.md` 중 PEB-009·010, 같은 폴더의 `05_RED_TEAM.md` 중 P5 재감사. 원 자료에는 `Issue #85 기록` (비공개 원본)과 `Issue #68 기록` (비공개 원본)이 지목되어 있습니다. 비공개 원본을 직접 열 수 없는 외부 독자를 위해 내부 링크는 제공하지 않았으며, 개인 일정·과목·메일 원문도 옮기지 않았습니다.

## 2. 작업자의 PASS를 어떻게 해석할 것인가

AI 작업자가 “완료”라고 말해도 실제 provider 상태, 검토한 코드 revision, 허용한 부작용 범위가 서로 다를 수 있습니다. 이를 배우며 결과 보고서에 **증거의 종류와 검증 대상**을 붙이는 작은 JS 모듈을 남겼습니다. [`evaluateCanaryEvidence(report)`](../code/personal-ai/src/lived-canary-evidence.js)는 고정된 assertion ID, 필수 필드, **가상 fixture 기준 식별자**, 부작용 지표를 검토합니다. 공개된 이 코드는 **합성 예제의 자기 일관성 검사기**입니다. `SYNTHETIC_FIXTURE`는 `REHEARSAL_ONLY`와 짝이 맞아야 하고, 실제 provider 재조회 근거가 없는 `LIVED_SANITIZED` 입력은 이 공개 버전에서 **반드시 INVALID**로 거절하도록 수정했습니다. 구조가 맞아도 필수 assertion이나 부작용 지표가 기대값과 다르면 `FAIL` 등으로 판정합니다.

예를 들어 제공된 합성 GitHub 입력은 `crossScopeSideEffects: 0`이므로 구조가 유효하고 판정은 `PASS`입니다. 같은 값을 1로 바꾸고 결과를 `FAIL`로 보고하면 검증기는 `METRIC_crossScopeSideEffects`를 실패 지점으로 돌려줍니다. 값은 1인데 결과만 `PASS`라고 쓰면 보고 결과와 계산 결과가 맞지 않아 `INVALID`가 됩니다. 이 구분은 “문제가 발견된 시험”과 “문제를 숨긴 보고서”를 다르게 다루기 위한 것입니다.

실행 명령은 [`package.json`](../code/personal-ai/package.json)에 정의된 그대로입니다. Node.js가 있으면 추가 패키지 설치 없이 실행됩니다.

```sh
cd code/personal-ai
npm run validate
```

이 명령은 [합성 입력](../code/personal-ai/fixtures/github-pass.synthetic.json)을 [CLI](../code/personal-ai/scripts/validate-lived-canary-evidence.mjs)에 넘깁니다. 정상 입력의 핵심 출력은 `"schemaValid": true`, `"verdict": "PASS"`입니다. CLI의 종료 코드는 PASS 0, 구조 오류 1, 유효하지만 PASS가 아닌 판정 2입니다. 별도의 [로컬 회귀 기록](../evidence/personal-ai/local-regression.json)에는 합성 조건 7개 중 7개가 예상 판정과 일치했고 `providerCalls: 0`이라고 적혀 있습니다. 이는 판정 로직의 로컬 시험이지 GitHub 권한 부여, 실제 메일 발송, Task 갱신 성공의 증거가 아닙니다. 이전의 “실패까지 성공으로 착각할 수 있다”는 경험을 코드의 입력 계약과 오류 출력으로 남겼다는 데 의미가 있습니다.

검증 모듈 자체에도 한계가 있습니다. 입력 `report`의 관찰값이 사실인지 직접 provider에 접속해 확인하지 않으며, 코드에 고정된 `PREPARED_AGAINST` 값은 공개 예제의 **가상 참조 문자열**이며, 실제 비공개 Git SHA나 provider의 최신 상태를 나타내지 않습니다. 실제 결과를 인정하려면 원 provider에서 영향을 받은 객체를 다시 읽고, 그 결과와 보고서를 대조해야 합니다.

## 3. 기술적으로 통과한 관리형 코딩 API를 기본 경로로 채택하지 않기

**2026-09-18 전후 K1 시험.** 관리형 코딩 API가 기존 GitHub 이슈 → 작업자 → 결과 통합 흐름보다 사용자 행동을 줄이는지 비교했습니다. 저는 실행·복구, 같은 HEAD에 대한 통합, 새 프로세스에서의 재조회라는 수용 조건을 제시했습니다. 구현과 시험은 작업자가 수행했습니다. 원본 증거 은행은 K1의 기술적 실행·복구 통과, 새 프로세스 재조회 2회, 중복 효과 0건을 기록합니다.

하지만 기술 통과 뒤에도 개발 이슈 접근 403, PR 접근 404와 설정·인증·복구를 사용자가 챙기는 부담이 남았습니다. 기록된 입력·출력 토큰 합계 32,805개는 이 한 시험의 사용량이지 일반화된 비용 절감률이 아닙니다. 실제 사용자 행동 감소가 입증되지 않아 이 경로를 기본 개발 방식으로 승격하지 않고 제한적 실험으로 남겼습니다. 제가 여기서 배운 기준은 모델이나 API가 일을 수행할 수 있다는 것과, 사용자가 더 쉽게 일을 끝낸다는 것을 따로 측정해야 한다는 점입니다.

**원본 근거:** 비공개 개인 저장소의 `portfolio/PORTFOLIO_MASTER_CASE_STUDY.md` 역할·아키텍처 변경 기록, `development_evidence/archive_mining_20260919/04_PORTFOLIO_EVIDENCE_BANK.md` 중 PEB-011 및 그곳에서 지목한 `K1 종료 기록` (비공개 원본)·`채택 판단` (비공개 원본). 장기 비용과 다른 작업 종류에서의 효과는 아직 측정하지 않았습니다.

## 지금 이어서 배우는 것

제 목표는 복잡한 “자율 에이전트”를 더 붙이는 것이 아니라, 작은 업무 하나에서 **원본 읽기 → 허용된 변경 → 원본 재조회 → 사용자에게 남는 효과 확인**을 재현하는 것입니다. 다음에는 학업 일정의 미존재 Task 경로와 반복 실사용, 작업자 보고서의 실제 provider 대조, 사용자 행동 수의 변화를 각각 분리해 기록하려 합니다. 이 페이지의 로컬 코드는 합성 검증 예제이고, 로봇 실험·물리 시연이나 완성된 개인 비서의 증거로 사용하지 않습니다.
